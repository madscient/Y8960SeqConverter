# MGSDRV のデータを Y8SQ に変換できるか（調査）

**この文書は、MGSDRV の演奏データ（`.MGS`）を Y8SQ に変換できるかを調べた結果を
持つ。** 読者は、このリポジトリで作業する AI と開発者、および Y8SQ 形式に何を
足すかを決める人。まだ変換器には入っていない。決めたことは `doc/plan.md` に移す。

確度の印は `doc/plan.md` と同じ: **確認済み**（走らせて確かめた。方法を添える）、
**未検証**、**推測**（根拠を添える）。資料に書いてあるだけでこちらが確かめていない
ものは **出典** と書く。

## 結論

**変換はできる。ただし不完全になる。** 音符・休符・音長・テンポ・オクターブ・音量・
音色・SCC の波形・Q・スラー・ループ・ノイズ・ハードウェアエンベロープ・
レジスタ書き込み・リズムは Y8SQ に写る。次のものは写らないか、近似になる。

1. 音程 LFO（`h`）
2. ソフトウェアエンベロープの大半。とくに FM に掛けるもの
3. 音程の自動変化（`p`）
4. 17 トラックを使う曲（Y8SQ は 16 トラックまで）
5. 1 トラック 2048 バイトを越える曲

どれも実データで使われている（下記「実データで数えたもの」）。MuSICA で
ビブラートとポルタメントを落としたのと同じ種類の欠落だが、**MGSDRV は FM にも
ソフトウェアエンベロープを掛けるので、落とすと音色の印象が変わる曲が MuSICA より
多い**（推測。根拠は、88 本中 54 本が FM で `@e` を使っていること）。

**データの形は、変換器を書くのに足りるだけ分かる。** 公式の仕様書は無い。
第三者の解析文書と MML の解説書がある。実データ 88 本を解析文書のコマンド表どおりに
最後まで読めた（下記）。**分からないのは値の意味の細部**で、エンベロープ・LFO・
ポルタメント・デチューンの単位や速さがこれにあたる（下記「資料から決まらないこと」）。

## MGS の形（要点）

細部は解析文書に譲る。変換に効くところだけを書く。

- ASCII の見出し（`"MGS"`、版 3 文字、タイトル、`1A`）のあとにバイナリの見出しが
  続く。バイナリの見出しはフラグ（FM 9 音かリズム付きか、機種コード、LFO の
  モード、圧縮）、テンポ、トラック 0-17 のオフセットを持つ（出典）
- トラック 0 は演奏しない。FM のユーザー音色（YM2413 のレジスタ 8 バイト）、
  ROM 音色の割り当て、エンベロープ、SCC の波形、音律表、制御文字列を持つ（出典）
- トラックの割り当ては PSG 1-3、SCC 4-8、FM 9-17。リズム付きなら FM 9-14、
  リズム 15（出典）
- **音長は四分音符 48 step で、Y8SQ の tick と同じ刻み**（出典）。1 バイトで
  1-256 step
- ループは `[n` … `|` … `]` で、16 段まで入れ子にできる（出典）。`|` は
  「最後の周なら抜ける」
- **版 304 より前（`MGS300` など）は音長を 1/60 秒で持つ**（出典）。実データの
  4 本がこれで、OPLLDRV・MuSICA と同じ扱いができる
- 圧縮されたデータ（版の 1 文字目が `A`）がある。展開の手順は逆コンパイラにある。
  実データに圧縮されたものは無く、展開は**未検証**

### テンポ

**MGSDRV は 1/60 秒の割り込みで動き、テンポ命令は 48 バイトの表を持つ**（出典）。

- 表を 2 ビットずつ 192 個に割ると、合計が floor(14400 ÷ テンポ) になる
  （**確認済み** ―― 実データに出る 13 種のテンポ 75・80・100・110・114・120・130・
  140・142・149・150・155・160 のすべてで数えた。外れたものは 0）
- この表は全音符 192 step の各 step に割り当てるフレーム数だと考えられる（推測。
  根拠は合計が全音符のフレーム数になることと、解説書の「最短音長＝14400 ÷ テンポ」）
- **このため MGSDRV の実際の速さは、名目のテンポより少し速い。** 全音符は
  floor(14400 ÷ T) フレームで、端数を切り捨てる。T142 では 101.41 フレームが
  101 フレームになり、約 0.4% 速い（推測。上の解釈が正しければ算術で出る）
- 表をどの位置から引くか（トラックの頭からの step 数か、テンポ命令からか）は
  資料に無い

## 写し方の見立て

**Y8SQ 側は `../Y8960BasicExtension/doc/bytecode.md` と `basic-reference.md` を
読んだ見立てで、変換器を書いて確かめてはいない**（未検証）。

### 写るもの

| MGS | Y8SQ | 備考 |
|---|---|---|
| 音符・休符（`2n` `3n` `2C` `3C`） | 音符・`0C` | |
| `o` `>` `<` | `80` `40` `41` | FM と PSG のオクターブの関係は未確認（下記） |
| `l`、`^` | 音長 | `^` はコンパイル時に音長へ足し込まれる（推測。根拠は、合計が 256 を越えると誤りになるという解説書の記述と、1 バイトの音長の上限が一致すること） |
| `t`、`#tempo` | `84` | 下記「時間の写し方」 |
| `v` | `81`（4*n*＋67） | 初期値は MGS が `v0`、Y8SQ が `V8`。頭で必ず書く |
| `v+` `v-` `(` `)` | `81` | Y8SQ に相対の音量は無い。変換器が値を追う。周ごとに値が変わるループは展開が要る |
| `q1`-`q8` | `83` | |
| `&` | `45` | |
| `@n`（FM） | `82` 1-15（ROM 音色）、`85`（ユーザー音色） | `@#` の割り当てを引く。ユーザー音色の 8 バイトから 12 バイトへの直しは OPLLDRV の `83h` と同じ |
| `@n`（SCC） | `85`（波形。チャンク `02`） | 実データの最大は FM と SCC を合わせて 10 本で、音色集合の 32 本に収まる |
| `n`（ノイズ周波数） | `E0` でレジスタ 06h | |
| `/n`（PSG のトーンとノイズ） | `82`（SSGS のミキサの bit5・bit6） | |
| `s` `m`（ハードウェアエンベロープ） | `B0` `DC` | |
| `y`（FM・リズム） | `E0` | OPLLEX が受け付ける範囲は元のチップのレジスタを覆う |
| `so` `sf` | `E0`（20h＋CH の bit5、マスク付き） | MuSICA と同じ |
| `/`（FM の強制キーオフ） | `E0`（20h＋CH の bit4 を落とす） | 推測。根拠は OPLLEX が 20h-28h の書き込みを受け付けること |
| `[n` … `]`、`[0` | `42` … `E2`（0 は無限） | 入れ子は 4 段まで。深いものは内側を展開する |
| `\|` | `E1` `D3` のブロックで「最後の周は残りを飛ばす」を作る | 推測。Y8SQ のブロックの規則を読んだかぎりでは書ける。書けなければ最後の周を展開する |
| リズムの発声 | `C8` | 楽器のビットの並び（bsmch）は同じ |
| リズムの音量（`v`*楽器*、`v`） | `D8`、`A9` | 相対の `47` は変換器が値を追う |

### 近似になるもの

| MGS | 近似の仕方 | 失うもの |
|---|---|---|
| `\`、`@\`（デチューン） | `D0`（セント） | 単位が分周値か F-Number なら、セントは音の高さで変わる。音符ごとに `D0` を書けば合うが、バイトが増える |
| `_`（ポルタメント） | `D2`（セント） | ±1200 セントを越える幅は書けない。変化の曲線と所要時間が同じかは未確認 |
| `@r`（AL AR DR SL SR RR、各 0-255） | `B2` とチャンク `04` | Y8SQ はアタックが 0 から始まり、サスティンで減衰しない（AL と SR が無い）。速さの刻みも粗い |
| `@e` のうち音量だけのもの | `B2` に寄せる | 任意の音量の並び・保持・スライドは ADSR にならない。音符ごとに `81` を並べれば合うが、バイトが大きく増える |
| `k`（キーオフ後の消え方） | `B2` で、アタックとディケイを最速にしたエンベロープ | `@e` と同時に使うときは表せない |
| `q0`（FM でキーオフしない） | 次の音符の前に `45` | 推測。OPLL はキーオン中にキーオンを書いても鳴らし直さないので、同じに聞こえると見た |

### 写らないもの

| MGS | 理由 |
|---|---|
| `h`（音程 LFO、三角波）、`ho` `hf` `hi` `@p` | Y8SQ に LFO が無い。`D1` に展開すると 2048 バイトに収まらない見込み（推測。MuSICA のビブラートと同じ見積もり） |
| `p`（PSG・SCC の音程を自動で下げる） | 同上 |
| FM と SCC に掛けた `@e` `@r`（`49`） | Y8SQ のソフトウェアエンベロープは SSGS と SCC だけ。FM には無い |
| `@e` の中の音色の切り替え・レジスタ書き込み・周波数の加算・ノイズとモードの変更・繰り返し | Y8SQ のエンベロープは音量だけ |
| `#psg_tune` `#opll_tune`（音律表） | Y8SQ は平均律で、変えられるのは A4 の周波数だけ。実データに使用例は無い |
| `#machine_id`（機種ごとの音量の補正） | 補正の中身が資料に無い |
| `ko`（リズムを叩くたびに音を切らない。MGS の初期状態） | Y8SQ の読み手は叩くたびに 5 つの楽器をすべて止める。OPLLDRV と同じ違い |
| `@m` `@o` `@f` `$`（ホストへの通知） | 演奏には要らない。実データに使用例は無い |
| 17 トラック目 | Y8SQ は 16 トラックまで |

## Y8SQ に不足しているもの

上の「写らないもの」「近似になるもの」のうち、Y8SQ の側に足せば写るものを、実データで
使っている曲の多い順に並べる。**どれを足すかは Y8SQ 形式の持ち主が決めることで、
ここでは候補として挙げるだけ。**

| | 使う曲（88 本中） | 足すとしたら |
|---|--:|---|
| 1. 音程 LFO | FM 61、PSG 39、SCC 24 | ディレイ・深さ・速さを持つ三角波のビブラート。MuSICA のビブラートもこれで写る |
| 2. FM のソフトウェアエンベロープ | 54 | 音量を時間で動かす仕組みを FM 音源系にも。FM では出力オペレータの減衰に足す |
| 3. 任意の形のエンベロープ | 音量だけの `@e` が 66、音量以外の命令を含む `@e` が 59 | 音量の列（保持・スライド・繰り返し）を持つレコード。音色・ノイズ・高さを動かすものまで入れるかは別に決める |
| 4. トラック 1 本の大きさ | 2048 バイトを越える見込みが 16（下記の概算） | 上限を上げる |
| 5. 音程の連続した変化 | PSG 23（`p`） | 1 フレームあたりのベンド量を持つスイープ。LFO を入れるなら同じ機構で書ける |
| 6. トラックの数 | 9（17 トラックを使う） | 17 本以上。MuSICA でも 85 本中 20 本が当たる |
| 7. ADSR の拡張 | `@r` 5、`k` は PSG 32・SCC 18 | アタックの開始レベルとサスティン中の減衰 |
| 8. 1 バイトを越えるテンポ | 0 | `84` は 255 まで。MGS は 2047 まで書ける |
| 9. ループの入れ子 | 2（最大 6 段） | 変換器が展開すれば済む。足さなくてよい |

## 時間の写し方

2 通りある。どちらにするかは未決。

| | 案 A: step を tick にする | 案 B: 1 フレームを 1 tick にする（T75） |
|---|---|---|
| テンポ | MGS のテンポをそのまま `84` に | 頭に `84 75` を 1 つ |
| 音長 | step の数をそのまま | 表を引いてフレーム数に直す |
| 速さ | MGSDRV より少し遅く鳴る（上記「テンポ」。T142 で約 0.4%） | MGSDRV と同じフレームで鳴る |
| 楽譜としての音長 | 残る | 失われる（OPLLDRV・MuSICA の変換と同じ） |
| 分からないこと | なし | 表をどの位置から引くか。間違えても 1 音あたり 1 フレームほどずれるだけで、全音符ごとに合計は合う（推測） |
| テンポ 256 以上 | 書けない（実データには無い） | 書ける |

案 B を推す。理由は、既存の 2 形式と同じ写し方で、元の機械と同じ時間で鳴るから。
前提は、MGSDRV が上の表のとおりにフレームを数えていること。

## 資料から決まらないこと

**値の時間の単位と大きさ。** 文書には範囲しか書かれていない。

| もの | 分からないこと |
|---|---|
| `@e` のカウント、`@r` の各レート、`k` | 1 カウントが 1/60 秒か（推測。ドライバが 1/60 秒の割り込みで動くため） |
| `h` | 速さと深さの単位、`#lfo_mode` の差 |
| `\` | 単位（分周値か、F-Number か、セントか）。解説書は「正の数で周波数が高くなる」とだけ書く |
| `_` | 所要時間（次の音符の長さか）と曲線 |
| `p` | 1 フレームあたりの変化量 |
| 音の高さ | 既定の音律表。PSG の O4A が 440Hz か（推測。MSX の慣例）。FM のオクターブが PSG より 1 つ低いか（推測。FM-BIOS と MuSICA がそうなので） |
| 音量 | FM の `v` を減衰量にどう直すか。SCC の音量を表を通さずに書くか |
| `#machine_id` | 補正の中身 |
| テンポの表 | どの位置から引くか |

決め方は 3 通りある。

1. MGSDRV を動かして、チップへの書き込みを記録する。最も確か。上記「配布条件で
   気を付けること」の判断が先に要る
2. 作者に問い合わせる
3. 実機か Y8960 で耳で比べる。粗い

## 実データで数えたもの

**確認済み** ―― 上記の 2 つのリポジトリと MGSDRV の作例から集めた `.MGS` を、
中身の重複を除いて 88 本読んだ。数えたスクリプトは解析文書のコマンド表どおりに
読むもので、リポジトリには入れていない。88 本すべてのトラックが `FF` まで読めた。
未知のコマンドは 0。

- 版は `313` が 84 本、`300` が 4 本。圧縮されたものは 0
- FM 9 音が 42 本、リズム付きが 46 本。機種コード 2 が 29 本、ほかは 0
- 音符を持つトラックの数が 17 の曲が 9 本
- テンポは 61-240。途中でテンポを変える曲が 5 本
- ループの入れ子が 5 段以上の曲が 2 本（最大 6 段）。`|` は 71 本、無限ループは 74 本
- 音律表を持つ曲は 0
- 機能ごとの使用（曲の数 / 出現の数）

| 機能 | FM | PSG | SCC |
|---|---|---|---|
| LFO（`h`） | 61 / 545 | 39 / 106 | 24 / 103 |
| ポルタメント（`_`） | 35 / 4527 | 19 / 894 | 10 / 239 |
| `@e` `@r` を音色に写す（`49`） | 54 / 5351 | ―― | 31 / 1396 |
| デチューン（`\`、0 以外） | 47 / 255 | 22 / 42 | 12 / 96 |
| デチューン（`@\`） | 47 / 221 | 22 / 49 | 18 / 102 |
| `p`（0 以外） | ―― | 23 / 356 | 0 |
| `k`（0 以外） | ―― | 32 / 83 | 18 / 78 |
| 相対の音量 | 68 / 4420 | 31 / 2291 | 20 / 1109 |

  ほかに、ハードウェアエンベロープ 16 / 2112、リズムの相対の音量 11 / 886、
  `kf` 12 / 32、FM の `y` 25 / 57、リズムの `y` 27 / 2622、`q0` 2 / 12、FM の
  強制キーオフ 3 / 35。`@m` `@o` `@f` `$` は 0
- トラックが選ぶエンベロープ（PSG の `@n`、FM と SCC の `@e` `@r`）のうち、
  音量の命令と繰り返しだけでできた `@e` を使う曲が 66 本、音色・ノイズ・モード・
  周波数・レジスタの命令を含む `@e` を使う曲が 59 本、`@r` を使う曲が 5 本
  （1 本が複数に当たる）
- **Y8SQ のトラックの大きさの概算で、2048 バイトを越えるトラックを持つ曲が 16 本**
  （最大 4197 バイト）。推測 ―― 案 A の写し方で、イベントごとに Y8SQ のバイト数を
  足しただけのもの。LFO の展開は含まない。ループは展開しない

## 作るとしたら

- 入力の判定に `"MGS"` の見出しを足す。BSAVE の見出しも配置番地も要らない
  （オフセットはすべて相対。出典）
- `Song` の音長は 1/60 秒を前提にしている（`src/core/song.h`）。案 B ならそのまま
  使える。案 A なら音長の単位を持たせる
- イベントの種類が増える: デチューン、ポルタメント、ハードウェアエンベロープ、
  ミキサ、ノイズ、ループの抜け、相対の音量
- 規模の見積もり（推測。既存の `source.cpp` と `convert.cpp` の大きさから）: 読み込みが
  400 行ほど、変換の追加が 500 行ほど。試験と `doc/conversion.md` の節が要る

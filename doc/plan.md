## 目的と範囲

OPLLDRV（FM-BIOS の演奏ドライバ）と MuSICA の演奏データ（バイナリ）を、
**Y8960 BASIC Extension の `MSAVE` が書き出すのと同じ Y8SQ ブロック**に変換する
コマンドラインツール。Windows / Linux / macOS。

- 入力は**ドライバが読むバイナリ**。MuSICA の MML（`.MSD`）や音色ファイル
  （`.VCD`）は読まない
- 出力の仕様は `../Y8960BasicExtension/doc/bytecode.md`
- **再生は範囲外。** 鳴らすのは Y8960Sequencer（`../Y8960Sequencer`）

## 決定事項

### 開発言語は C++17、ビルドは CMake 3.18 以上。コアと CLI の2層

- Y8960MMLCompiler に合わせた（こちらの判断、2026-09-27）。利用者には確認して
  いない
- **理由。** 兄弟と同じ道具立てなら、ビルド手順・リリースの作り方・Y8SQ の
  書き出し部分をそのまま流用できる
- **前提。** 兄弟リポジトリが C++17 と CMake のままであること
- 変えるときの値段: 書き直し。コアは入力の解析と出力の組み立てしか持たないので
  2000 行程度の見込み（**推測** ―― 兄弟のコアが 3500 行で、MML の解析を持たない
  ぶん小さい）

### コマンド名は `y8conv`

- 利用者の決定（2026-09-27）

### 時間は T75 で 1 フレーム＝1 tick

- 利用者の決定（2026-09-27）
- 元の2形式の音長は 1/60 秒の割り込み回数（`tempo_list.md`）。Y8960 は
  四分音符 48 tick で、1 tick ＝ 60 / (テンポ × 48) 秒。テンポ 75 で
  ちょうど 1/60 秒になる。**丸めが一切入らない**
- 楽譜としての音長（四分音符が何 tick か）は元データに無い情報なので、
  変換後の音長は譜面上の値とは対応しない。再生の時間は正確
- **前提。** 元データが NTSC の 60Hz 割り込みで作られていること。PAL（50Hz）の
  機械で作った曲は、元の機械で聞いたより 1.2 倍速くなる

### 1 イベントの音長は 8191 tick まで。越えるものは分ける

- 読み手（ROM の `TRKGETLEN`、プレイヤーの `readLength`）は音長を 15 ビットで
  読むが、ゲートは音長を Q 回足して 16 ビットに入れる（ROM の `TRKGATE`、
  プレイヤーの `setGate`）。8191 × 8 ＝ 65528 で溢れない（**確認済み** ――
  両方のコードを読んだ。走らせてはいない）
- 分けるときは、音符はタイ（`45`）でつなぎ、休符と待ちは同じイベントを重ねる

### MuSICA の PSG／SCC のソフトウェアエンベロープは、Y8960 のソフトウェアエンベロープに写す

- Y8960 BASIC Extension が `B2`（エンベロープ番号）とチャンク `04`（AR・DR・SL・RR）を
  入れた（2026-09-27、向こうのコミット 1dc7618）。83h を読んだ時点で、先頭 4 バイトを
  エンベロープとして登録し、`B2` で名指す。同じ中身は 1 つにまとめ、1 から番号を振る。
  31 個を越えたら誤り
- **値の写し方。** チャンク `04` の AR・DR・RR は、MuSICA と同じ（上位 4 ビット＝
  割り込みの数、下位 4 ビット＝変化量）のバイトで、どちらも 1-15（向こうのコミット
  8ab257e から）。MuSICA のバイトをそのまま書く。上位か下位が 0 のバイト（MuSICA では
  256 割り込みに 1 回、動かない）は書けないので、速さの最も近いバイトに寄せて警告する。
  どちらの 0 も `F1` に寄る。利用者の決定（2026-10-02、こちらの提案どおり）
- サンプル 85 本の音色のバイト 5934 個は、すべて MuSICA の 33 通りの組だった
  （**確認済み** ―― 走査スクリプトで数えた）ので、寄せるバイトは出ない
- 経緯: 8ab257e より前のチャンク `04` は 0-32 の番号（33 通りの表の索引）で、変換器は
  表を逆引きしていた
- **前提。** Y8960 のエンベロープの動きが MuSICA と同じであること（向こうの文書は
  「MuSICA と同じ」と書く）。下の未決事項に、読み比べて気づいた差を 1 つ置いた
- 経緯: 利用者の決定で、エンベロープが Y8960 に入るまでは変換しなかった（音色の
  4 バイトを読み捨てて警告）。その前は利用者の決定で「音量イベントに展開し、2048 バイトを越えたら誤り」として
  実装した。展開ありの成功は 85 本中 34 本、展開なしは 58 本（**確認済み** ――
  両方で変換して数えた）。展開のモデルは推測だった（仕様書にはアタックの始点、
  チャンネル音量との合成、リリースの扱いが無い）

### OPLLDRV の拡張音色（82h）は Y8960 のプリセット @n に写す。ROM の吸い出しで上書きできる

- 利用者の決定（2026-09-27）
- 既定は同じ番号の Y8960 プリセット（MSX-MUSIC BASIC と同じ 64 音色の名前の並び）。
  レコードは Y8960MMLCompiler と同じ音色表を、同じ権利表記を付けて同梱する
- 利用者が自分の機械の ROM から吸い出した 64 × 8 バイトの OPLL 音色表を渡せば、
  それを使ってユーザー音色として厳密に写す
- **既定の経路でも移調は掛けない**（チャンク `01` の移調を 0 にする）。FM-BIOS の
  `82h`（`int_e_voice`）は ROM の 8 バイトを OPLL のレジスタ 0-7 に書くだけで、
  チャンネルの作業域（`opllwork.mac`）に移調の欄は無く、`int_note` は音符番号から
  直接ブロックと F-Number を出す（**確認済み** ―― ソースを読んだ。MUSIC・MUSIC_tR・
  music_midi の 3 版でこの部分は同じ）
- Y8960 のプリセットの移調（丸めたあと 0 でないものが 41 本）は MSX-AUDIO BASIC の
  もので、そのうち 37 本は ML が MSX-MUSIC の ROM の同じ番号の音色と同じ（**確認済み**
  ―― 表どうしを比べた）。移調は BASIC の側の補正で、OPLLDRV の音には入っていない
- 経緯: チャンク `01` が移調を持つようになった（向こうのコミット 1b06823）とき、
  「`@n` が鳴るとおりに鳴らす」としていったん移調を入れた（こちらの判断）。利用者の
  指示で FM-BIOS のソースを読み、上のとおり 0 にした（2026-10-02）
- サンプルでは FM-PAC の FMPAC0（38 番 ＋12、46 番 −12）と FMPAC2（27 番 −31）が
  既定の経路で `82h` を使う（**確認済み** ―― 走査した）
- **前提。** 拡張音色の中身は FMPAC と MSX-MUSIC 内蔵 ROM で違う
  （uniskie 氏の OPLDRV_tool が `/cv:fmpac` と `/cv:music` を分けている）。
  どちらの音で作られた曲かはデータからは分からない

### 読み手が拒むものは書かない

Y8960Sequencer の `block.cpp` と ROM の `MLOAD` が拒む形（トラック 2048 バイト
超、音色集合 32 本超）は、書き出さずに誤りにする。部分的に鳴るブロックを
黙って作らない。

### 音色表は兄弟と同じ生成スクリプトで作る。OPL2EX のリズム音色は持たない

- こちらの判断（2026-09-27）。`tools/gen_voicedata.py` は Y8960MMLCompiler の
  ものを写し、リズム音色 3 本を出力から外した
- **理由。** リズム音色は OPL2EX にしか要らず、このツールは OPLLEX しか使わない。
  持たなければ、その 3 本にかかる CC BY-SA の表記の義務も持たない
- **前提。** 出力先が OPLLEX であること。OPL2EX に書く出力を足すなら、戻す

### 同じブロックの並びの繰り返しを、ループに畳む

- こちらの判断（2026-09-27）。MuSICA のシーケンスは「ブロックを何回」の並びだが、
  A B A B A B のような周期的な並びは回数を持てないので全部書かれている。
  各位置から最長の周期的な並びを探して入れ子の節にし、節ごとに「周ごとに状態が
  そろえばループ」を適用する
- 効果（**確認済み** ―― サンプル 85 本をエンベロープ展開なしで変換して数えた）:
  成功が 54 本から 57 本、2048 バイト超のトラックが 26 本から 19 本
- 同じブロックが連続するものは、回数を足して 1 つにする

### サステインは `E0` のマスク付き書き込みで写す

- OPLL の 20h＋CH の bit5。`E0 (20h+CH) 20h/00h DFh` で bit5 だけ書き換える
- **前提。** 読み手が音符を書くときに bit5 を保つこと。プレイヤーの
  `dev_opllex.cpp` の `setPitch` は「サステインと bit7-6 は `Y` のもの」として
  保つ（**確認済み** ―― コードを読んだ）。ROM も、音符を書くときに 20h＋CH の
  上位 4 ビットを保つ（`OPLL_SETPITCH`。サブエージェントがコードを読んだ。こちらでは
  読み直していない）

### リズムの音量は、楽器ごとの通常音量（`D8`）に写す。アクセントは使わない

- こちらの判断（2026-09-30）。Y8960 BASIC Extension が `D8`（楽器のビットマップと
  その楽器の通常音量）を入れた（向こうのコミット 0b40308）のに合わせた
- それまでは、Y8960 のリズムの音量が「通常」と「アクセント」の 2 つしか無かったので、
  打撃ごとに叩く楽器の音量を 2 つに振り分けていた（3 種類以上は寄せて警告）。
  `D8` なら元の楽器ごとの音量がそのまま写るので、`AA` とアクセントは使わない
- **その楽器を叩くときに書く。** 同じ値にしたい叩かない楽器は、同じ `D8` のビットに
  相乗りさせる（バイトが増えない）。5 つとも同じなら `A9`（1 バイト短い）
- **トラックの頭では、読み手の音量を不明として扱う。** 向こうの `bytecode.md` は
  リズムの音量を走行状態ではないとし、周の頭で戻さない（シーケンスを先頭から
  演奏し始めるときだけ 8 に戻す）。既定値 8 に頼ると、繰り返しの 2 周目が 1 周目の
  最後の音量で鳴る。それまでの実装は 8 に頼っていた
- **前提。** 読み手が `D8` の値を叩いた楽器の音量レジスタにそのまま使うこと。
  ROM は `D8` で値を控え、打撃のときに 5 つの楽器すべてを書く（叩かない楽器も）。
  `81`、周の頭、`VOLUME` でもその場で書く。値 *n* は、シーケンスの音量が最大なら
  減衰量 15 − *n* になる（`RHY_SETVOL` `OPLL_RHYLEV`。サブエージェントがコードを
  読んだ。こちらでは読み直していない）
- 変えるときの値段: `hit()` 1 か所と試験 2 項目

### FM の音色は、チャンク `01` の 12 バイトのレジスタイメージで書く

- Y8SQ 形式の変更（向こうのコミット 1b06823）に合わせた（2026-10-02）。それまでは
  BASIC と同じ 32 バイトだった
- OPLL の 8 バイト（83h、`--rom-voices`）は `recordFromOpll` が直接 12 バイトにする。
  ROM の `OPLL_SETUSER` の逆で、試験は `OPLL_SETUSER` を試験側に書き写したものとの
  往復で見る
- プリセットは、同梱の 32 バイトの表（生成物）を `voicepack.cpp` の `packVoice` が
  詰める。ROM の `TAB_VOIPACK` と、兄弟の Y8960MMLCompiler の `packVoice` と同じ
  詰め方。表を 12 バイトで生成しないのは、兄弟と同じ表と生成スクリプトを保つため
- 音色の名前は 12 バイトに入らないので、同じレジスタの音色は 1 本にまとまる
  （それまでは名前の違いで別の本になっていた）

### OPLLEX の内蔵音色は `82` の 1-15 で書く

- `82` の番号は、OPLLEX では bit5-4 がバンク、bit3-0 がバンクの中の音色になった
  （向こうのコミット 1b06823）。YM2413 の内蔵音色はバンク 0 なので、元の音色番号を
  そのまま書く。それまでは 65-79（MML の `@65`-`@79`）を書いていた。ROM は bit7-6 を
  無視するので、古い出力も同じ音で鳴る（**確認済み** ―― ROM の `OPLL_SETVOICE` を
  読んだ。走らせてはいない）

### MuSICA の SCC は、音量の表を通さない（`B3 0`）

- 利用者の決定（2026-10-02、こちらの提案どおり）。SCC のトラックの頭に `B3 0` を書く
- Y8960 BASIC Extension は SCC の音量を既定で表に通す（`V1`-`V7` がどれも 1 になる）。
  MuSICA は 0-15 の値を SCC の音量レジスタにそのまま書く（`doc/musica-driver.md`
  「出力」）。`B3 0` なら静的な音量もソフトウェアエンベロープの出力も、元と同じ値が
  レジスタに届く
- 見送った案: `V` を表の逆引きで近い値に寄せる（エンベロープの出力は直らず、元の
  5・7・9・11・13・14 は表に無い）。何もしない（元の小さい音量が潰れる）
- `B3` は周の頭で 1 に戻るが、トラックの頭は周ごとに通るので、頭に 1 つ置けば足りる
- 変えるときの値段: `build()` の 1 行と試験 1 項目

### OPLLDRV の `82h` `83h` はユーザー音色を設定するだけで、選ばない

- FM-BIOS の `int_e_voice` `int_u_voice` はレジスタ 0-7 に書くだけで、音色番号
  （30h＋CH の上位 4 ビット）を書くのは `70h`-`7Fh`（`int_v_select`）だけ
  （**確認済み** ―― ソースを読んだ）。こちらの判断で合わせた（2026-10-02）
- 経緯: それまでは uniskie 氏の OPLDRV_tool の読み方に合わせて、`82h` `83h` で
  音色 0 を選んでいた（**推測**と明記していた）
- サンプルの OPLLDRV 21 曲では、`82h` のあとの音符はすべて `70h` の下で鳴り、
  出力は変わらない（**確認済み** ―― 走査し、直す前後の出力をバイト単位で比べた）

### OPLLDRV の音色と音量の初期値は、FM-BIOS の起動時の値

- FM-BIOS の `MSTART` は Q、レガート、キーオフしか設定し直さない。音色と音量は
  チップに残っている値のまま（**確認済み** ―― ソースを読んだ）。起動時の `INIOPL`
  がメロディの全チャンネルを音色 11、減衰量 3 にし、`rhythm_ini`（リズムモードで
  演奏を始めるたび）がリズムの全楽器を減衰量 3 にする
- 変換器は起動時の値を使う（こちらの判断、2026-10-02）。それまでは音色を MuSICA の
  `7Ah`（10）にしていた。音量 3 とリズムの 3 は、それまでの推測と一致した

### リズムの止め方は、元と違うところをそのままにする

- 利用者の決定（2026-10-02）。打撃のとき、どの楽器を止めるかが元と違うところがある
  （**確認済み** ―― どれもコードを読んだ）
- Y8960 の ROM（`OPLL_RHYSTRIKE`）もプレイヤー（`rhythmStrike`）も、0Eh のキーの
  ビットを 5 つとも落としてから、叩く楽器を立てる
- `BGM.BIN` も同じ（D609h）。楽器の無い打撃（`20h`）でも 5 つとも落とすので、
  鳴り残りが切れる。変換器はこれを `0E` にしていて、止めない。サンプルでは
  16 本に 85 回ある（**確認済み** ―― 走査した）
- FM-BIOS は叩く楽器だけを落とす（`rhythm_on`）。OPLLDRV の曲では、叩かない楽器の
  鳴り残りが、変換後は次の打撃で切れる。Y8960 にはこれを避けるイベントが無い
- 見送った案: MuSICA の楽器の無い打撃を `C8 00` と音長にする（1 回 1 バイト増える）。
  ROM とプレイヤーはこれで 5 つとも止める。ただし向こうの `bytecode.md` は楽器 0 個の
  `C8` の意味を書いておらず、`basic-reference.md` は「並べたすべての楽器をいったん
  止めてから鳴らす」と書いていて、コードの「5 つすべて」とずれている
- **前提。** Y8960 の読み手の打撃が、いまの動作（5 つとも止める）のままであること

## 変換の写し方（設計）

詳細は成果物の `doc/conversion.md` にある。ここには決めた理由と
確度だけを置く。

### 入力の見分け方

| 形 | 見分け方 |
|---|---|
| BSAVE 形式 | 先頭が `FE`、続く 6 バイトが開始・終了・実行アドレス。開始アドレスが配置番地 |
| OPLLDRV | 本体の先頭 2 バイトが `000Eh`（メロディ 6 音＋リズム）か `0012h`（メロディ 9 音） |
| MuSICA | 本体の先頭が `00` か `01`、続く 17 個の番地がどれも `0000h` か本体の中を指す |

- MuSICA の番地はすべて絶対番地なので、配置番地が要る。BSAVE 形式ならヘッダから、
  RAW なら引数で受け取る
- OPLLDRV のヘッダは相対オフセットだが、ユーザー音色（83h）だけは絶対番地
- **ヘッダの先頭の語は、それ自身が 1 本目のオフセット。** 9 音構成ではデータが
  `+12H` から始まる。uniskie 氏の資料の表の `+14H` は誤記。FM-BIOS の `MSTART` は
  先頭の語が `12h` ならメロディモード、それ以外ならリズムモードとし、語を順に
  オフセットとして読む（**確認済み** ―― ソースと当時の仕様書を読んだ）

### チャンネルの割り当て

| 元 | Y8960 |
|---|---|
| FM メロディ 1-9 | OPLLEX1 の 0-8 |
| FM リズム | OPLLEX1 の 10 |
| MuSICA PSG 10-12 | SSGS の 0-2 |
| MuSICA SCC 13-17 | SCC の 0-4 |

トラック番号は、使っているチャンネルに頭から振る。

### 音の高さ

**元と同じ周波数で鳴る番号に写す。** Y8960 の O4A はどの音源でも 440Hz
（プレイヤーの `freqtab.cpp` を読んだ）。

- MuSICA の PSG と SCC は O4A が 440Hz なので、元の n は Y8960 の n ＋ 11
- **MuSICA の FM は O4 をブロック 3 で鳴らし、O4A が約 218Hz**（`BGM.BIN` の音程の
  処理を読んだ）。元の n は Y8960 の n − 1
- 確かめ方（**確認済み**）: 1 音だけの曲を変換してプレイヤーで WAV にし、自己相関で
  基本周波数を測った。FM の O4A が 221Hz、PSG の O4A が 440Hz
- 最初は両方とも n ＋ 11 にしていた（推測）。FM が 1 オクターブ高く鳴っていた
- OPLLDRV の FM も MuSICA と同じ。FM-BIOS の `f_num_data` は C が 171（0ABh）、A が
  288（120h）で、`int_note` はブロックを（音符番号 − 1）÷ 12 にする（**確認済み** ――
  ソースを読んだ。走らせてはいない）

### 音量

Y8960 の音量は 0-127 で、1 が 0.75 dB。`V`*n* は 4*n* ＋ 67 で、初期値は 99（`V8`）。
4 ビットの音量しか持たない OPLLEX の FM・SSGS・SCC の読み手は、(127 − 音量) を 4 で
割った段だけ 15 から下げる（向こうの `bytecode.md`「走行状態」）。元の 16 段の
レベル L を 4L ＋ 67 に写せば、ちょうど段 L に戻る。FM の元の値は減衰量なので、
L ＝ 15 − 値。

- 経緯: 向こうのコミット ba467b6 より前は `V`*n* が 8*n* ＋ 7（読み手は `>> 3`）で、
  変換器もそれに合わせていた

### ループとブロック

MuSICA のシーケンスは（ブロック、演奏回数）の並び。回数が 2 以上なら
`42`…`E2` で囲む。**ループの本体は、入口の走行状態が周ごとに同じときだけ
ループにする。** 変換が走行状態（オクターブ、レガート、エンベロープ）に依存する
ので、1 周目の出口の状態が入口と違えば、1 周目を展開してから残りをループに
する。それでも合わなければ全部展開する。

## 見送った案

- **メタ情報（チャンク `80`）にタイトルを書く。** 見送った（利用者の決定、2026-10-02、
  こちらの提案どおり）。理由: 書くかどうかは形式の上で任意で、元データにタイトルの
  欄があるかを調べていない。書くなら ASCII の `20h`-`7Eh` だけ

- **8Ch を OPLL に届くものとして FM トラックへ移す。** 見送った。理由: `BGM.BIN` を
  読むと、8Ch はチャンネルの音源に書く（FM は WRTOPL、PSG は WRTPSG、SCC は
  9880h＋番号）。Ys2 の数曲が PSG チャンネルから 0Eh・18h・28h・36h-38h を書いて
  いるのは、元の機械でも音に届かない書き込みで、落とせばよい

- **ループの判定を「出力のバイト列が同じか」でする。** 見送った。理由: バイト列が
  同じでも、出口の走行状態（オクターブ、レガート、エンベロープの位相）が入口と
  違えば、2 周目の同じバイト列は違う音になる。状態の一致で判定する
